# MythCanvas 静态内容 / 动态数据改造计划

> 状态：已批准的默认架构基线（Architecture Baseline）
>
> 版本：1.0
>
> 日期：2026-09-02
>
> 适用范围：公共内容页面、内容仓库、搜索、关系图、站点地图、创作上下文、用户数据与 Cloudflare 存储边界

## 1. 决策摘要

MythCanvas 后续默认采用以下数据架构：

```text
源代码中的已发布规范内容
  → 构建期校验和索引
  → Astro 预渲染 / Worker 中的静态只读目录
  → 公共页面、SEO、搜索、关系图、AI 创作规范上下文

用户与运营产生的可变数据
  → Worker API
  → D1 / KV / R2
  → 登录态、收藏、生成任务、投稿审核、用户作品和事件
```

核心规则：

1. `Mythology`、`World`、`Scene`、`Character`、`MythStory`、`CharacterRelation`、规范名称、概念、主张、来源、分类、`VisualDNA`、`CanonicalDesign`、已发布 `Style` 和 `OutputSpec` 默认是版本化静态内容。
2. 公共实体页、公共关系图、规范内容搜索和站点地图不得依赖 D1 才能成功响应。
3. D1 只作为可变业务数据的权威源，例如账户、收藏、生成任务、投稿、审核、用户作品归属和事件记录。
4. R2 保存图片及其衍生文件；KV 保存会话、限流、配置和可丢弃缓存。浏览器存储只能做缓存，不能成为内容权威源。
5. 策展作品与用户生成作品分轨：策展作品元数据进入静态发布清单；用户生成、社区投稿和审核中作品留在 D1 + R2。
6. 现有 D1 内容表在迁移期间保留为兼容镜像，不再作为公共页面的默认运行时数据源；删除或归档必须另行审计和批准。

这不是把整个应用改成纯静态站点。Astro 继续使用 Cloudflare Worker 运行动态 API；只把稳定公共内容从“每次请求查询 D1”改为“构建期发布、运行时只读”。

## 2. 背景与问题

### 2.1 事故暴露的问题

当前生产实现以 D1 为公共内容主数据源，静态数据仅在绑定缺失、查询失败或额度耗尽时兜底。近期 D1 读取额度耗尽导致公共页面不可用，说明当前边界存在三个结构性问题：

- 稳定内容的可用性被绑定到运行时数据库和套餐额度。
- 一个实体详情页可能并行读取多个仓库，列表和关系解析又可能读取大集合，放大每次访问的行读取量。
- 静态数据和 D1 同时存在，但 D1 优先，使两套内容源增加复杂度，却没有换来公共内容的可靠性收益。

已上线的“额度错误时回退静态数据”是必要止血，但不是目标架构。它仍然会先消耗 D1，并且只有失败后才走静态路径。

### 2.2 业务事实

神话体系、角色身份、世界、场景、关系、来源、概念和规范设计是编辑发布内容。它们会修订，但不会按用户请求实时变化。对这类数据，重新构建和部署是合理的发布动作。

账户、收藏、生成任务、投稿、审核状态和用户作品归属则会随用户操作变化，需要事务性和运行时持久化。这两类数据不应共用同一个默认读取路径。

## 3. 当前代码评估

### 3.1 已有可复用基础

仓库已经具备迁移所需的大部分基础：

- `src/content/registry.ts` 注册 Greek、Norse、Maya、Japanese、Egyptian 等结构化内容包。
- `src/data/mythologies.ts` 和 `src/data/seed.ts` 提供类型化的神话、世界、角色、场景、作品、风格和变体种子数据。
- `src/lib/content/stories.ts` 已经把结构化内容包作为已迁移神话故事的权威源。
- `src/lib/content/repositories/` 已有领域仓库接口和静态回退实现。
- `scripts/sync-structured-content.mjs` 能把静态内容同步到 D1，可在过渡期继续作为兼容工具。
- D1 migrations 已区分内容、用户、收藏、生成、投稿、审核和事件等表结构。
- R2 媒体路由已经支持不可变缓存响应；KV 已用于会话等运行态数据。

因此，第一至第三阶段不需要读取线上 D1，可以直接基于仓库内容和 schema 开始。线上 D1 只在动态数据核对、兼容镜像审计和最终退役决策时需要只读盘点。

### 3.2 当前主要耦合

目前首页、探索、神话、角色、世界、壁纸、搜索、创建页和站点地图等公共路由会读取 `Astro.locals.runtime.env.DB`。其中角色详情会组合神话、作品、名称、解释、变体、世界、角色和关系等多个仓库查询。

当前仓库的典型读取顺序是：

```text
存在 D1 binding
  → 查询 D1
  → 查询成功：返回 D1 数据
  → 配额或查询失败：回退静态内容
```

目标顺序应改为：

```text
公共规范内容
  → 直接读取静态目录，不接收 D1 参数

用户 / 社区 / 运营数据
  → 明确进入动态仓库，查询 D1
```

### 3.3 当前构建链路问题

`npm run check` 当前包含 `npm run content:import -- --mythology=all`。这使“内容校验/构建”和“写入 D1”耦合。目标是：

- `check` 只做静态内容校验、构建、类型检查和部署 dry-run，不写远端数据。
- D1 同步改成显式兼容或运营命令，不能是公共站点构建成功的前提。
- 内容发布的必要产物是静态目录和站点构建结果，而不是 D1 导入成功。

## 4. 目标数据所有权

| 数据类别 | 权威源 | 运行时读取 | 发布方式 | 说明 |
| --- | --- | --- | --- | --- |
| Mythology / VisualDNA | `src/content` / 类型化静态数据 | 静态目录 | PR + 构建部署 | 公共规范内容 |
| World / Scene / CanonicalDesign | `src/content` | 静态目录 | PR + 构建部署 | 公共规范内容 |
| Character / CharacterRelation | `src/content` | 静态目录 | PR + 构建部署 | 关系索引在构建期生成 |
| MythStory / 来源 / 主张 / 概念 / 分类 | `src/content` | 静态目录 | PR + 构建部署 | SEO 正文不可依赖 D1 |
| 已发布 Style / OutputSpec | 版本化静态定义 | 静态目录 | PR + 构建部署 | 供展示和生成上下文使用 |
| 策展 Artwork 元数据 | 静态发布清单 | 静态目录 | 审核后晋升到 PR | 图片文件仍在 R2/CDN |
| 图片、缩略图、参考图 | R2 | R2/CDN | 上传 + 不可变 key | 元数据保留来源和尺寸 |
| 用户、账户、登录 nonce | D1 | Worker API | 运行时事务 | 动态数据 |
| 会话、限流、短期配置 | KV | Worker API | 运行时 | KV 不是关系数据权威源 |
| 收藏 | D1 | Worker API / 小岛 | 运行时事务 | 页面先静态渲染，再叠加用户状态 |
| 生成任务与生成结果归属 | D1 + R2 | Worker API | 运行时 | D1 元数据，R2 文件 |
| 投稿、审核、用户作品 | D1 + R2 | Worker API | 运行时 | 未晋升前不进入规范内容目录 |
| 下载/行为分析 | Analytics Engine 或 D1 的采样/批处理 | 异步写入 | 运行时 | 不阻塞主请求 |
| 浏览器 IndexedDB/localStorage | 无权威数据 | 可选缓存 | 版本化、可丢弃 | 不作为内容数据库 |

### 4.1 作品双轨模型

`Artwork` 需要按生命周期区分，而不是把全部作品都做成静态或全部放进 D1：

```text
CuratedArtwork
  = 已审核、长期公开、参与实体页/SEO/站点地图的作品
  = 静态元数据清单 + R2 文件

GeneratedArtwork / CommunityArtwork
  = 用户生成、投稿、审核中或实时公开的作品
  = D1 元数据 + R2 文件
```

社区作品可以在探索页以独立动态区块加载，但不得让其接口失败拖垮规范内容页面。作品通过审核并决定成为长期策展资产后，由晋升流程生成或修改静态清单并走正常部署。

### 4.2 CharacterVariant 和 ReferenceAsset

- 已发布、参与公共角色身份和生成约束的 `CharacterVariant` 应进入版本化静态内容。
- 草稿、实验或后台审核中的变体可以暂存 D1；发布时晋升到静态内容。
- `ReferenceAsset` 的二进制文件在 R2；所有权、来源和审核记录可以在 D1。
- 已批准且生成链路必须稳定依赖的参考资产，需要在静态发布清单中保留稳定 ID、R2 key、哈希和来源摘要。

## 5. 目标运行架构

```text
                         ┌──────────────────────────┐
Git / src/content ──────▶│ 校验 + 编译 PublicCatalog │
                         └────────────┬─────────────┘
                                      │
                 ┌────────────────────┼────────────────────┐
                 ▼                    ▼                    ▼
          Astro 预渲染页面      静态搜索/关系索引      生成上下文解析器
                 │                    │                    │
                 └────────────────────┴────────────────────┘
                                      │
                                  Cloudflare CDN

Browser interaction ──▶ Worker API ──┬─▶ D1：用户和业务状态
                                      ├─▶ KV：会话/限流/缓存
                                      └─▶ R2：图片和衍生文件
```

### 5.1 PublicContentCatalog

建立单一的只读公共目录接口，统一当前 `src/data`、`src/content/registry.ts` 和各静态回退数组：

```ts
interface PublicContentCatalog {
  mythologies: readonly Mythology[];
  worlds: readonly World[];
  scenes: readonly Scene[];
  characters: readonly Character[];
  characterRelations: readonly CharacterRelation[];
  stories: readonly MythStory[];
  styles: readonly Style[];
  outputSpecs: readonly OutputSpec[];
  curatedArtworks: readonly Artwork[];
}
```

目录加载时生成只读索引：

- `id → entity`、`slug → entity`
- `mythologyId → characters/worlds/scenes/stories/artworks`
- `characterId → worlds/stories/relations/artworks/variants`
- `worldId → characters/stories/scenes/artworks`
- 搜索文档、关系邻接表、站点地图 URL 和图片 URL

页面不得各自扫描大数组或重新拼装关系。索引应在模块初始化或构建期生成，并由契约测试验证。

### 5.2 仓库边界

目标接口按所有权拆分：

```text
PublicContentRepository
  - 不接收 D1 binding
  - 读取 PublicContentCatalog
  - 服务公共页面、SEO、搜索、关系图和生成规范上下文

UserDataRepository
  - 接收 D1/KV
  - 服务账户、会话、收藏和个人空间

GenerationRepository
  - 接收 D1/R2
  - 服务任务、结果、归属和状态

CommunityArtworkRepository
  - 接收 D1/R2
  - 服务投稿、审核和实时社区作品
```

禁止继续使用“同一个内容仓库根据是否有 DB 决定数据源”的隐式行为。数据源必须从接口类型和调用位置可见。

## 6. 路由与渲染矩阵

| 路由 | 目标模式 | D1 依赖 | 说明 |
| --- | --- | --- | --- |
| `/` | 预渲染 | 0 | 策展内容静态；用户状态独立加载 |
| `/mythology`、`/mythology/:slug` | 预渲染 | 0 | `getStaticPaths` + 静态目录 |
| `/mythology/:mythologySlug/:storySlug` | 预渲染 | 0 | 正文、关系和来源完整输出 |
| `/character`、`/character/:slug` | 预渲染 | 0 | 收藏状态通过小岛/API 叠加 |
| `/world`、`/world/:slug` | 预渲染 | 0 | 关系由静态索引提供 |
| `/wallpaper`、策展 `/wallpaper/:slug` | 预渲染 | 0 | 用户/社区作品使用独立动态入口 |
| `/explore` | 静态主体 + 可选动态区块 | 主体为 0 | 社区区块失败不影响主体 |
| `/search` | 静态索引 | 0 | 社区搜索可作为独立增强 |
| `/create` | 静态壳和规范选项 + 动态 API | 页面为 0 | 生成请求仍是动态的 |
| sitemap / image sitemap | 预渲染 | 0 | 从静态目录生成 |
| `/login`、`/register`、`/password` | 可预渲染壳 | 0 | 表单提交到动态 API |
| `/my`、`/admin` | SSR | 需要 | 用户态/运营态页面 |
| `/api/auth/*`、收藏、生成、投稿、审核 | Worker API | 需要 | 明确的动态边界 |
| `/media/*` | Worker/R2 或 CDN | 不需要 D1 | 不可变缓存和范围请求 |

`astro.config.mjs` 可以继续保持 `output: "server"`；公共路由通过 `prerender = true` 和 `getStaticPaths` 生成，动态 API 保持 Worker 运行。无需改造成 React SPA，也无需一次性切换成全站静态输出。

## 7. 搜索、关系图与站点地图

### 7.1 搜索

为规范内容生成轻量搜索文档，至少包含：

- 实体类型、ID、slug、名称、别名、英文名、摘要
- mythology、world、character 和 topic 关系
- 可控的拼音/别名字段（若已有）
- 预计算权重，不在浏览器加载全部领域对象

索引可以随构建产出 JSON，由页面服务端直接使用或按版本由客户端懒加载。IndexedDB 仅可缓存该版本化 JSON；缓存丢失时必须可以重新下载。

社区作品搜索若有实时需求，使用单独 D1 接口并合并展示，不能替代静态规范搜索。

### 7.2 角色关系图

`/api/character-graph` 应只读取静态邻接表。可选择：

- 在页面构建时直接内联当前角色的最小图数据；或
- 保留 Worker API，但响应仅基于静态目录并设置 CDN 缓存。

两种方式都必须满足 D1 完全不可用时关系图仍可工作。

### 7.3 站点地图

普通 sitemap、图片 sitemap 和 sitemap index 都从静态目录生成。社区实时作品不默认进入主 sitemap；只有达到公开、稳定、可索引标准后才通过单独的受控流程纳入。

## 8. 内容发布与运营工作流

### 8.1 规范内容发布

```text
编辑内容文件
  → schema / 引用 / 唯一性 / 来源校验
  → 生成静态索引
  → 构建预览
  → PR 审核
  → 部署
```

所有内容更新都有 Git 版本、审查记录和可回滚提交。部署失败不会修改线上内容数据库。

### 8.2 投稿晋升

```text
D1 投稿/生成记录 + R2 文件
  → 审核通过
  → 导出候选静态条目
  → 校验来源、许可、尺寸、实体关系和稳定 R2 key
  → PR
  → 部署为 CuratedArtwork / 已发布内容
```

后台“审核通过”不应直接让未版本化数据成为规范实体页的强依赖。若未来需要非技术编辑即时发布，应先设计受审计的内容发布服务和静态快照产物，并通过 ADR 修改本基线。

### 8.3 D1 内容镜像

过渡期允许把静态目录同步到 D1，目的仅限于：

- 兼容旧后台或脚本；
- 数据对比和迁移审计；
- 为尚未切换的内部工具提供短期读模型。

镜像不是公共页面的权威源，也不能是构建和部署的硬依赖。同步命令必须显式执行并区分 local/remote。

## 9. 分阶段执行计划

### Phase 0 — 基线与护栏

目标：先阻止架构继续反向扩散。

- 将本文、`docs/ARCHITECTURE.md` 和 `AGENTS.md` 设为默认规则。
- 建立公共路由 D1 依赖清单和动态 API 白名单。
- 添加架构检查：公共页面不得导入 D1 adapter 或访问 `runtime.env.DB`。
- 保留当前静态回退作为迁移期生产保护。
- 记录迁移前 URL、构建产物、核心页面状态和 D1 读取基线。

验收：新增技术方案默认先判断“规范静态内容”还是“用户/运营动态数据”，例外必须写 ADR。

### Phase 1 — 统一静态目录

目标：消除 `src/data`、内容 registry 和仓库 fallback 之间的重复权威源。

- 定义 `PublicContentCatalog` 和静态索引构建器。
- 把现有 mythology、seed 和 structured bundles 通过一个入口组合。
- 对 ID、slug、外键、关系方向、发布状态、图片尺寸和来源做完整校验。
- 明确策展 Artwork、已发布 CharacterVariant、Style 和 OutputSpec 的静态清单。
- 为目录查询、关系图和生成上下文增加契约测试。

验收：每个已发布实体只有一个明确权威定义；所有关系在构建期可解析，无悬空引用。

### Phase 2 — 公共仓库切换

目标：公共内容读取路径完全不接触 D1。

- 新建或重构 `PublicContentRepository`，删除公共方法的可选 `db` 参数。
- 切换首页、探索、神话、角色、世界、故事、策展作品、创建选项和 prompt preview 的规范内容读取。
- 将角色详情的全量 world/character 扫描改为索引查询。
- 将社区/用户作品读取迁到明确的动态 repository。
- 旧 D1 内容 adapter 保留为短期兼容模块，不再被公共路由导入。

验收：关闭或移除 D1 binding 后，全部公共规范页面仍返回完整内容；请求级 D1 读取为 0。

### Phase 3 — 预渲染与静态派生产物

目标：把公开内容从 Worker 请求计算进一步前移到构建期。

- 为实体详情路由实现 `getStaticPaths` 并启用 `prerender = true`。
- 预渲染主页、列表页、法律页、登录/注册壳和 sitemap。
- 生成搜索文档、关系邻接表和 sitemap 数据。
- 保持收藏、登录菜单和生成交互为最小岛或客户端增强。
- 验证 404、canonical、OpenGraph、JSON-LD 和内部链接与迁移前一致。

验收：规范内容即使 Worker 的 D1 不可用也能由 CDN/静态构建稳定提供；核心 SEO 内容无需客户端请求。

### Phase 4 — Artwork 双轨改造

目标：静态策展与动态用户作品互不拖累。

- 定义 `CuratedArtwork` 发布清单及校验规则。
- 定义 `GeneratedArtwork` / `CommunityArtwork` 动态仓库。
- 探索页将社区内容做成独立可降级区块。
- 建立“审核记录 → 候选静态条目 → PR → 发布”的晋升工具。
- 确保 R2 key 稳定、不可变，并记录尺寸、格式、hash、来源和许可。

验收：策展页面 0 D1 读取；社区 API 故障不影响策展内容；晋升结果可审计和回滚。

### Phase 5 — 动态数据隔离与额度治理

目标：D1 只为真正动态的用户操作付费。

- 逐项审计账户、收藏、生成、投稿、审核、个人空间 API 的查询数和索引。
- 避免列表 N+1；为常用用户查询添加必要索引和上限。
- 将非关键 analytics 写入改为异步、采样、批处理或 Analytics Engine。
- KV 只保存会话、限流、配置和可丢弃缓存。
- 增加 D1 额度、错误率、每端点读取量和慢查询观测。

验收：D1 使用量与真实用户写操作和个性化读取成正比，不再随公共爬虫和静态页面浏览线性增长。

### Phase 6 — 构建与同步解耦

目标：部署公共站点不再依赖 D1 导入。

- 从 `npm run check` 移除隐式 `content:import`。
- `content:validate` 扩展为静态目录、关系、搜索和路由校验。
- 保留显式 `content:mirror:d1:local` / `content:mirror:d1:remote` 一类兼容命令，远端写入必须主动触发。
- 在 CI 中构建站点并验证公共路由不引用 D1。

验收：在没有 Cloudflare 数据绑定的 CI 环境中可以完成内容校验和 Astro 构建。

### Phase 7 — 兼容层退役

目标：去掉长期双源复杂度，但不冒险删除数据。

- 对线上 D1 做一次只读盘点，比较静态目录与内容表差异。
- 确认所有公共、后台和脚本消费者已经切换。
- 将内容镜像表标记为非权威、只读或归档。
- 单独提交任何 drop/清理 migration，并准备备份和恢复方案。
- 移除临时 `legacy-d1` 内容开关和失败回退分支。

验收：仓库中不存在含糊的“D1 或静态二选一”公共内容读取；动态表数据完整保留。

## 10. 测试与验收标准

### 10.1 架构验收

- 公共规范路由每次请求 D1 读取数：`0`。
- 公共页面、搜索、关系图、prompt 规范上下文和 sitemap 在 D1 不可用时均可工作。
- `src/pages` 的公共页面不直接访问 `Astro.locals.runtime.env.DB`。
- 规范内容 repository 的公共接口不接收 `D1Database`。
- 浏览器端不保存不可恢复的权威内容。

### 10.2 内容验收

- 所有已发布实体 ID 和 slug 唯一。
- 所有引用可解析，关系两端存在且 mythology 归属符合约束。
- `Character`、`CharacterVariant`、`Style`、`OutputSpec` 继续正交。
- 图片包含稳定 key/URL、尺寸、alt、格式和来源/许可信息。
- 静态目录与现有公开 URL 保持 100% 路由兼容。

### 10.3 可用性与性能验收

- 模拟 D1 binding 缺失、查询失败和配额耗尽，公共页面仍为 200（不存在的实体除外）。
- 社区动态区块失败时显示可降级状态，不影响页面主内容。
- 无每张卡片、每条关系或每个 sitemap URL 的运行时数据库查询。
- R2 稳定资产使用不可变缓存；主图尺寸明确，避免 CLS。
- 构建时间和静态产物大小设预算，索引过大时按 mythology/type 分片。

### 10.4 发布验收

- `npm run content:validate`
- `npm run typecheck`
- `npm run build`
- `wrangler deploy --dry-run`
- 关键路由 smoke test
- 部署后检查 D1 读取量未随公共访问增长

## 11. 上线与回滚策略

### 11.1 上线顺序

1. 先发布静态目录和兼容测试，不改变页面数据源。
2. 按领域切换：Mythology/Story → Character/Relation → World/Scene → CuratedArtwork/Search/Sitemap。
3. 每批切换后比较 URL、页面实体数、关系数和 SEO 输出。
4. 再启用路由预渲染。
5. 最后解耦 D1 同步并退役兼容读取。

### 11.2 临时回滚

迁移期间可以保留短期发布开关，例如 `PUBLIC_CONTENT_SOURCE=static|legacy-d1`，但必须满足：

- 默认值始终是 `static`；
- 只用于整批发布回滚，不在请求内自动探测；
- 不允许长期形成双写/双读；
- Phase 7 后删除。

D1 内容表在稳定期内不删除，因此应用代码可以通过回滚部署恢复旧读取路径。静态内容本身通过 Git 提交和上一版本构建产物回滚。

## 12. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 静态内容和 D1 镜像不一致 | 静态内容为权威；提供差异报告，不做隐式覆盖 |
| 构建时间或 bundle 变大 | 分离构建期目录与浏览器索引；按类型/神话分片 |
| 内容更新需要部署 | 这是规范内容的发布门槛；通过自动预览和部署缩短周期 |
| 运营希望即时改正文 | 先走受审计导出/PR；真正 CMS 需求另立 ADR |
| 社区作品需要实时公开 | 独立动态 feed，不并入规范页面关键路径 |
| AI 生成需要最新已批准设定 | 生成 Worker 使用同版本静态目录；部署版本可追踪 |
| 老脚本依赖 D1 内容表 | 保留显式镜像和兼容 adapter，逐个迁移后退役 |
| 预渲染页面叠加收藏状态 | 服务端输出稳定内容，最小客户端增强查询当前用户状态 |

## 13. 非目标

本次改造不包括：

- 把 Astro 重写为 React SPA 或更换框架；
- 把 R2 图片打包进应用代码；
- 把用户收藏、生成或投稿做成本地浏览器数据；
- 立即删除 D1 内容表或迁移所有历史数据；
- 在没有真实需求前建设完整 CMS；
- 改变现有产品信息架构、Light/Dark 主题或领域正交规则。

## 14. 后续技术方案的默认判定规则

以后新增数据或功能时，按以下顺序判断：

1. 数据是否对所有用户一致，并且只在编辑发布时变化？是：进入版本化静态内容和 `PublicContentCatalog`。
2. 数据是否由账户行为、任务状态、审核流程或实时运营产生？是：进入 D1，通过动态 API 访问。
3. 数据是否为图片或二进制文件？是：进入 R2，元数据按静态策展或动态用户归属分别管理。
4. 数据是否为会话、限流、配置或可重新生成的缓存？是：进入 KV 或适当缓存层。
5. 数据是否只是为了让前端少请求？是：可以缓存，但不能改变权威源。

任何要让公共规范内容重新依赖 D1 的方案，必须单独提交 ADR，说明：实时编辑需求、事务需求、失败降级、配额预算、缓存策略、SEO 影响、迁移和回滚方案。没有该 ADR 和明确批准，默认拒绝此例外。

## 15. 完成定义

这项架构改造只有在以下条件全部满足时才算完成：

- 公共规范内容已统一到静态权威目录。
- 公共实体页、搜索、关系图和 sitemap 均为零 D1 依赖。
- 策展作品与用户/社区作品完成双轨拆分。
- D1、KV、R2 的所有权边界可从代码结构直接识别。
- 构建与 D1 内容导入已经解耦。
- 动态 API 经过查询预算、索引和故障测试。
- 旧 D1 内容镜像完成审计，兼容层已退役或有明确到期计划。
- `docs/ARCHITECTURE.md`、`AGENTS.md`、CI 检查和实际代码保持一致。
