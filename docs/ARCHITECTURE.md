# MythCanvas Architecture

## 1. Current repository assessment

The repository is currently a Cloudflare Astro Blog Starter rather than a MythCanvas application.

Current useful foundations:

- Astro 5 + TypeScript
- `@astrojs/cloudflare`
- Cloudflare Workers deployment
- Sitemap, RSS and MDX integrations
- Basic SEO head component
- Simple `src/components`, `src/layouts`, `src/pages`, `src/content`, `src/styles` separation

Current gaps:

- `index.astro`, Header/Footer, about/blog routes are still starter content
- No MythCanvas domain model
- No Mythology / Realm / Character / Artwork routes
- No Light/Dark semantic theme system
- No Civilization Visual DNA implementation
- No React integration yet
- No D1/R2/KV bindings yet
- No AI generation orchestration
- No user/favorite/download model
- No image pipeline or image sitemap

The correct strategy is to **evolve the Astro starter, not replace it with a full SPA**.

---

## 2. Architectural principles

1. **Content-first Astro**: crawlable content should be generated by Astro SSR/SSG.
2. **Islands only when needed**: search autocomplete, filters, favorites, creator, theme toggle and user state can become islands.
3. **One application theme**: Light/Dark are semantic token variants, not separate page implementations.
4. **Domain-first content model**: Mythology → Realm → Character → Scene → Artwork.
5. **SEO is architecture**: metadata, structured data, internal links, image semantics and sitemap generation are part of page implementation.
6. **Cloudflare-native backend**: Workers + D1 + R2 + KV, introduced incrementally.
7. **Image is a first-class asset**: artwork metadata and derivatives must be modeled explicitly.
8. **Avoid premature abstraction**: build shared UI only after at least two real use sites unless the component is a primitive.

## 4. Domain model

### Mythology

```ts
type Mythology = {
  id: string;
  slug: string;
  name: string;
  nameEn: string;
  summary: string;
  visualDna: VisualDNA;
  heroArtworkId?: string;
};
```

### Realm

```ts
type Realm = {
  id: string;
  mythologyId: string;
  slug: string;
  name: string;
  nameEn?: string;
  summary: string;
  canonicalDesign: CanonicalDesign;
  landmarkIds: string[];
};
```

### Character

```ts
type Character = {
  id: string;
  mythologyId: string;
  realmIds: string[];
  slug: string;
  name: string;
  nameEn?: string;
  summary: string;
  symbols: string[];
  canonicalDesign: CanonicalDesign;
};
```

### Artwork

```ts
type Artwork = {
  id: string;
  slug: string;
  type: 'character' | 'realm' | 'scene' | 'creature' | 'architecture';
  mythologyId: string;
  realmId?: string;
  characterIds?: string[];
  styleId: string;
  moodIds: string[];
  image: ImageAsset;
  license: LicenseMeta;
  promptMeta?: PromptMeta;
  reviewStatus: 'draft' | 'approved' | 'hidden';
};
```

### Core distinction

- **Theme** = how the application chrome is displayed.
- **Visual DNA** = cultural identity of a mythology.
- **Canonical Design** = identity anchors for a character/realm.
- **Style Variant** = how a specific artwork is rendered.

Never merge these concepts into a single `theme` field.

## 5. Theme architecture

Use semantic tokens only.

```css
:root,
[data-theme='light'] {
  --bg-primary: ...;
  --surface: ...;
  --text-primary: ...;
  --accent: ...;
}

[data-theme='dark'] {
  --bg-primary: ...;
  --surface: ...;
  --text-primary: ...;
  --accent: ...;
}
```

Components consume semantic tokens:

```css
.card {
  color: var(--text-primary);
  background: var(--surface);
  border-color: var(--border);
}
```

Do not duplicate `.card-light` / `.card-dark` implementations.

Theme boot script must run before first paint to prevent FOUC/theme flash.

## 6. Rendering strategy

### Static / server-rendered by default

- Home
- Explore landing content
- Mythology
- Realm
- Character
- Artwork
- Style landing pages
- Editorial stories

These pages must include meaningful content without JavaScript.

### Islands

Use islands only for:

- Theme toggle
- Search suggestion
- Complex multi-filter UI
- Favorite state
- Login/user menu
- AI Creator
- Generation progress/results
- Device preview controls if necessary

Do not hydrate entire page shells.

---

## 7. Data evolution

### Stage 1 — seed data

Use typed TypeScript/JSON/Astro Content Collections so UX can be built without backend dependency.

### Stage 2 — D1 metadata

Move dynamic entities and user actions to D1:

- entities and relationships
- users
- favorites
- generation records
- download counters

### Stage 3 — R2 assets

R2 stores originals and generated derivatives. Persist image dimensions, aspect ratio, format, alt and attribution with each asset.

### Stage 4 — KV/cache

KV is appropriate for configuration, feature flags and precomputed hot lists; it is not the source of truth for relational content.

## 8. AI generation boundary

The browser never talks directly to model providers with secret keys.

```text
Creator UI
  → Worker API
  → validate/moderate request
  → enrich with Canonical Design + Civilization Visual DNA
  → provider adapter
  → generation result
  → persist metadata
  → R2 asset
  → return normalized result
```

Prompt construction should be server-owned so Character identity, Visual DNA and safety rules remain consistent.

---

## 9. SEO / GEO architecture

Every entity page must provide:

- canonical URL
- unique title/description
- explicit H1 and entity summary
- image alt text
- internal links to related entities
- OpenGraph/Twitter metadata
- JSON-LD where meaningful
- server-rendered core facts

Generate:

- regular sitemap
- image sitemap
- robots rules
- structured entity relationships

Do not hide mythology facts or artwork metadata behind client-only requests.

## 11. Definition of Done for a page

A page is not done until:

- Light and Dark both pass visual QA
- mobile/tablet/desktop layouts exist
- no core content depends on hydration
- images have dimensions + alt
- loading/empty/error states exist when relevant
- keyboard/focus behavior is usable
- metadata/canonical are correct
- related entity links are present
- no modern copyrighted IP design was copied as reference output
- build/check passes
