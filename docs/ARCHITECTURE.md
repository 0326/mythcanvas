# MythCanvas Architecture

## 1. Current repository assessment

MythCanvas is an Astro + Cloudflare application evolving toward a content-first mythology exploration and AI creation platform.

Current useful foundations:

- Astro 5 + TypeScript
- `@astrojs/cloudflare`
- Cloudflare Workers deployment
- D1 / R2 / KV runtime foundations
- Sitemap / SEO head infrastructure
- Domain repositories for Mythology / World / Character / Artwork / Scene / Style
- Light / Dark semantic theme system
- AI generation orchestration and structured character/style generation direction

Current architecture work should continue to **evolve the Astro application, not replace it with a full SPA**.

---

## 2. Architectural principles

1. **Content-first Astro**: crawlable content should be generated by Astro SSR/SSG.
2. **Islands only when needed**: search autocomplete, filters, favorites, creator, theme toggle and user state can become islands.
3. **One application theme**: Light/Dark are semantic token variants, not separate page implementations.
4. **Domain-first content model**: civilization context, visual entities, narrative entities and artwork must remain distinct.
5. **Mythology is a first-class system, Story is narrative**: `Mythology` represents a complete mythology system and owns its Visual DNA; concrete myths and legends use an independent `MythStory` entity.
6. **SEO is architecture**: metadata, structured data, internal links, image semantics and sitemap generation are part of page implementation.
7. **Cloudflare-native backend**: Workers + D1 + R2 + KV, introduced incrementally.
8. **Image is a first-class asset**: artwork metadata and derivatives must be modeled explicitly.
9. **Text is a first-class content asset for Myth Story**: story body, tradition/source notes and entity relations must be server-renderable and independently indexable.
10. **Avoid premature abstraction**: build shared UI only after at least two real use sites unless the component is a primitive.

Product naming and UX positioning are defined in `docs/CONTENT_POSITIONING.md`.

## 4. Domain model

### 4.1 Mythology — civilization / mythology-system context

```ts
type Mythology = {
  id: string;
  slug: string;
  name: string;
  nameEn: string;
  summary: string;
  visualDna: VisualDNA;
  heroArtworkId?: string;
};
```

`Mythology` owns cultural context and Civilization Visual DNA. It is a first-class system page and a horizontal context across Characters, Worlds, MythStories and Artworks.

It is not the concrete story body of “嫦娥奔月”“诸神黄昏” etc.; those belong to `MythStory`.

### 4.2 World — persistent mythic space

```ts
type World = {
  id: string;
  mythologyId: string;
  slug: string;
  name: string;
  nameEn?: string;
  summary: string;
  canonicalDesign: CanonicalDesign;
  landmarkIds: string[];
};
```

User-facing navigation groups `World + Scene` under **神域**.

### 4.3 Scene — reusable place / event-space concept

```ts
type Scene = {
  id: string;
  mythologyId: string;
  worldId?: string;
  slug: string;
  name: string;
  nameEn?: string;
  summary: string;
  canonicalDesign: CanonicalDesign;
};
```

A Scene can represent a localized visual place or reusable event-space, while World represents the persistent higher-level world/domain.

### 4.4 Character — mythic being / named figure

```ts
type Character = {
  id: string;
  mythologyId: string;
  worldIds: string[];
  slug: string;
  name: string;
  nameEn?: string;
  summary: string;
  symbols: string[];
  canonicalDesign: CanonicalDesign;
};
```

User-facing navigation calls this content family **神灵**. The technical name remains `Character` to preserve stable domain semantics.

### 4.5 MythStory — concrete narrative / legend

```ts
type MythStory = {
  id: string;
  slug: string;
  mythologyId: string;

  title: string;
  subtitle?: string;
  summary: string;
  body: string;

  topicIds: string[];
  characterIds: string[];
  worldIds: string[];
  sceneIds?: string[];
  artworkIds?: string[];

  readingMinutes?: number;
  tradition?: string;
  sourceNotes?: string[];

  heroImage?: ImageAsset;
  publishStatus: 'draft' | 'published';
  publishedAt?: string;
  updatedAt: string;
};
```

`MythStory` is the content model for a specific **故事 / 传说** under a Mythology system. It is not the entity behind the user-facing **神话** Tab.

Important relationships:

```text
Mythology
  ├── Character × N
  ├── World × N
  ├── Scene × N
  ├── MythStory × N
  └── Artwork × N

MythStory
  ↔ Character × N
  ↔ World × N
  ↔ Scene × N
  ↔ Artwork × N
```

Story and Mythology must not be collapsed into one model.

### 4.6 Artwork — visual interpretation

```ts
type Artwork = {
  id: string;
  slug: string;
  type: 'character' | 'world' | 'scene' | 'creature' | 'architecture';
  mythologyId: string;
  worldId?: string;
  characterIds?: string[];
  styleId: string;
  moodIds: string[];
  image: ImageAsset;
  license: LicenseMeta;
  promptMeta?: PromptMeta;
  reviewStatus: 'draft' | 'approved' | 'hidden';
};
```

A Story may reference multiple Artworks, but Story itself is not an Artwork subtype.

### 4.7 Core distinction

- **Theme** = how the application chrome is displayed.
- **Mythology** = civilization / mythology-system context.
- **MythStory** = concrete story / legend / narrative explanation.
- **Visual DNA** = cultural identity owned by Mythology.
- **Canonical Design** = identity anchors for Character / World.
- **Style Variant** = how a specific artwork is rendered.

Never merge these concepts into one `theme`, `type` or generic content field.

## 5. User-facing information architecture vs technical model

User-facing navigation:

```text
探索｜神灵｜神域｜神话｜AI 创作
```

Technical mapping:

```text
探索     → Artwork discovery
神灵     → Character
神域     → World + Scene
神话     → Mythology
故事/传说 → MythStory
AI 创作  → generation workflow
```

This distinction is intentional. UI naming can be literary and approachable while technical naming remains stable and explicit.

## 6. Theme architecture

Use semantic tokens only.

```css
:root,
[data-theme='light'] {
  --bg-primary: ...;
  --surface: ...;
  --text-primary: ...;
  --accent: ...;
}

[data-theme='dark'] {
  --bg-primary: ...;
  --surface: ...;
  --text-primary: ...;
  --accent: ...;
}
```

Components consume semantic tokens:

```css
.card {
  color: var(--text-primary);
  background: var(--surface);
  border-color: var(--border);
}
```

Do not duplicate `.card-light` / `.card-dark` implementations.

Theme boot script must run before first paint to prevent FOUC/theme flash.

Story pages use the same theme system; they must not introduce separate parchment / scroll themes.

## 7. Rendering strategy

### Static / server-rendered by default

- Home
- Explore landing content
- Myth story index
- Myth story detail
- Mythology civilization pages
- World
- Character
- Artwork
- Style landing pages

These pages must include meaningful content without JavaScript.

Story body, source/tradition notes and related entity links are core crawlable content and must not depend on client hydration.

### Islands

Use islands only for:

- Theme toggle
- Search suggestion
- Complex multi-filter UI
- Favorite state
- Login/user menu
- AI Creator
- Generation progress/results
- Device preview controls if necessary

Do not hydrate entire page shells.

## 8. Data evolution

### Stage 1 — editorial content / seed data

For early MythStory production, prefer Astro Content Collections or typed Markdown/MDX so writers can iterate without requiring a new admin system.

Recommended frontmatter shape mirrors `MythStory` relations:

```yaml
slug: change-flies-to-the-moon
mythologyId: myth-chinese
characterIds:
  - character-change
worldIds:
  - world-moon-palace
topicIds:
  - moon
  - love
tradition: 淮南子及后世嫦娥奔月传说
```

### Stage 2 — D1 metadata

Move dynamic entities and user actions to D1:

- entities and relationships
- Story index metadata if needed
- accounts / account_sessions
- favorites
- generation records
- download counters

Story long-form body can remain content-file based until editorial/admin requirements justify migration.

### Stage 3 — R2 assets

R2 stores originals and generated derivatives. Persist image dimensions, aspect ratio, format, alt and attribution with each asset.

### Stage 4 — KV/cache

KV is appropriate for configuration, feature flags and precomputed hot lists; it is not the source of truth for relational content.

## 9. AI generation boundary

The browser never talks directly to model providers with secret keys.

```text
Creator UI
  → Worker API
  → validate/moderate request
  → enrich with Canonical Design + Civilization Visual DNA
  → provider adapter
  → generation result
  → persist metadata
  → R2 asset
  → return normalized result
```

Prompt construction should be server-owned so Character identity, Visual DNA and safety rules remain consistent.

Story content may provide creation context, but Story prose must not be blindly injected into generation prompts. Resolve only structured Character / World / Scene / Style context needed for generation.

## 10. SEO / GEO architecture

Every entity page must provide:

- canonical URL
- unique title/description
- explicit H1 and entity summary
- image alt text
- internal links to related entities
- OpenGraph/Twitter metadata
- JSON-LD where meaningful
- server-rendered core facts

### Story pages additionally require

- full server-rendered article body
- `Article` / `CreativeWork` JSON-LD
- `datePublished` / `dateModified`
- author/editor attribution
- `tradition` / source notes when available
- links to related Character / World / Mythology

Generate:

- regular sitemap
- image sitemap
- robots rules
- structured entity relationships

Do not hide mythology facts, Story body or artwork metadata behind client-only requests.

## 11. Recommended migration sequence

### Phase A — information architecture

- Header naming: 角色 → 神灵, 世界 → 神域, 文明图鉴 → 神话
- Keep `/mythology/` as the canonical Mythology entry
- Keep `/mythology/{slug}` as the mythology-system aggregation page
- Reserve Story / MythStory for a later `/story/` or nested story route
- Add Mythology context to Character / World UI

### Phase B — Story MVP

- Define Content Collection schema for MythStory
- Build Story / MythStory only when there is a confirmed story content requirement
- Prefer `/story/` and `/story/{slug}/` if Story becomes a first-class route
- Publish 15–25 initial stories
- Add Civilization + Topic filtering

### Phase C — relation graph

- Character → related Stories
- World → Stories that happen here
- Story → Characters / Worlds / Artworks
- Search across Story title/summary/entities

### Phase D — SEO / GEO

- Article structured data
- canonical + sitemap
- source/tradition notes
- story/topic landing pages only when enough content exists

### Phase E — editorial tooling

Only after real editorial volume justifies it:

- Story admin editor
- relation picker
- source/version management
- scheduled publishing

## 12. Definition of Done for a page

A page is not done until:

- Light and Dark both pass visual QA
- mobile/tablet/desktop layouts exist
- no core content depends on hydration
- images have dimensions + alt
- loading/empty/error states exist when relevant
- keyboard/focus behavior is usable
- metadata/canonical are correct
- related entity links are present
- no modern copyrighted IP design was copied as reference output
- build/check passes

For Myth Story pages also require:

- readable long-form typography and content width
- Story body remains useful with JavaScript disabled
- related Character / World links exist
- tradition/source ambiguity is represented when relevant
- visual treatment remains editorial, not artwork-grid-first
