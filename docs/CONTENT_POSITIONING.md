# MythCanvas 内容定位与一级导航规范

> 状态：Product Canonical Addendum  
> 版本：V1.1  
> 日期：2026-08  
> 适用范围：后续产品设计、页面命名、信息架构、内容建模与 AI Coding。

## 1. 结论

MythCanvas 的一级内容导航统一收敛为：

```text
首页｜探索｜神灵｜神域｜神话｜AI 创作
```

其中三类核心内容页面形成明确分工：

| 用户名称 | 核心问题 | 内容形态 | 主要对象 |
|---|---|---|---|
| 神灵 | 谁存在于神话中？ | 强视觉 | Character |
| 神域 | 神话发生在哪里？ | 强视觉 | Realm + Scene |
| 神话 | 发生过什么？为什么如此？ | 文字叙事为主 | Story / Legend |

产品体验原则可概括为：

> **神灵、神域负责“看”；神话负责“读”；探索负责“发现”；AI 创作负责“创造”。**

这套职责边界作为后续页面设计的默认前提。

---

## 2. 为什么不再使用「角色 / 世界 / 文明图鉴」

### 2.1 「角色」改为「神灵」

「角色」是产品与游戏术语，缺少 MythCanvas 自身的神话语义。

「神祇」虽然更古典，但认知门槛高、语义偏窄，无法自然覆盖英雄、妖灵、精怪、半神和其他具名神话存在。

因此用户侧统一使用 **神灵**，其产品解释为：

> 探索诸神、英雄与传说中的存在。

技术对象仍沿用 `Character`，不因用户名称改变数据模型命名。

### 2.2 「世界」改为「神域」

「世界」过于泛化，无法体现产品内容特征。

「神域」用于承载神话空间与视觉场景，包括：

- 神界 / 冥界 / 天界等大世界
- 奥林匹斯、阿斯加德、天宫、高天原等 Realm
- 月宫、昆仑、世界树之根、冥界之门等地点与 Scene
- 神殿、遗迹、战场、异象等可持续扩展的视觉空间

技术上保持 `Realm` 与 `Scene` 两层对象，用户侧统一由「神域」作为入口组织。

### 2.3 「文明图鉴」改为「神话」

「文明图鉴」的问题是：

- 容易被理解为百科目录；
- 与视觉产品的核心体验割裂；
- 把「华夏 / 希腊 / 北欧」这种分类维度误当成一级内容对象；
- 无法承载具体故事、传说、事件和叙事关系。

新的「神话」定位不是视觉图鉴，而是 **神话故事与解释性内容的阅读入口**：

> 讲清楚诸神如何诞生、世界如何形成、人物为何行动、神域为何存在，以及不同传说之间如何关联。

因此「神话」页面应明显区别于神灵、神域：图片用于建立氛围和解释上下文，文字才是主体。

## 3. 文明的正确定位：全站分类轴，而不是一级 Tab

华夏、希腊、北欧、日本、埃及等 `Mythology` 不再作为与神灵、神域并列的一级内容类型，而作为横向组织全站内容的 **文明 / 神话体系分类轴**。

```text
                华夏神话
                    │
希腊神话 ───── Mythology ───── 北欧神话
                    │
                 日本神话
                    │
                 埃及神话

                    ↓
       ┌────────────┼────────────┐
       ↓            ↓            ↓
      神灵          神域          神话
   Character    Realm / Scene    Story
       ↓            ↓            ↓
       └──────── Artwork / Related Content ────────┘
```

因此：

- `Mythology` = 文明上下文 / 分类维度 / Visual DNA 所有者；
- `Character` = 神灵；
- `Realm + Scene` = 神域；
- `Story / Legend` = 神话叙事；
- `Artwork` = 可以关联任意上述对象的视觉作品。

### 文明入口仍然存在

文明不从产品中消失，而是从「一级 Tab」变为：

- 神灵页筛选条件；
- 神域页筛选条件；
- 神话页筛选与阅读入口；
- 搜索分组；
- 首页专题入口；
- `/mythology/{slug}` 文明聚合页 / SEO Landing Page；
- Civilization Visual DNA 的技术归属对象。

## 4. 一级导航职责

### 首页

负责品牌感知和少量精选入口，不承担完整内容浏览。

### 探索

定位：**视觉内容发现 Feed**。

回答：

> 现在有什么值得看的神话视觉？

主要内容：Artwork；支持文明、类型、画风、设备、排序等筛选。

### 神灵

定位：**神话人物视觉资产库**。

回答：

> 我想认识和继续探索某个神话人物。

主要内容：Character Canonical Design、变体、相关神域、相关神话、Artwork。

页面应保持强视觉，以肖像 / 全身视觉作为主体。

### 神域

定位：**神话世界、地点和场景的视觉探索入口**。

回答：

> 这些传说发生在哪里？这个世界是什么样子？

主要内容：Realm、Scene、地标、空间结构、相关神灵、相关神话、Artwork。

页面应保持强视觉，以环境概念图和空间关系作为主体。

### 神话

定位：**神话故事、传说与世界观解释入口**。

回答：

> 发生了什么？这些人物和世界为什么会变成这样？

主要内容：Story / Legend / Editorial Narrative。

默认是阅读产品，不做图片瀑布流，不做百科词条列表。

### AI 创作

定位：把神灵、神域、画风和输出规格组合为新的视觉作品。

## 5. 核心产品关系

未来推荐链路不再只围绕图片展开，而围绕四类内容互相跳转：

```text
Artwork
  ↔ 神灵 Character
  ↔ 神域 Realm / Scene
  ↔ 神话 Story
  ↔ 文明 Mythology
```

典型用户路径：

```text
看到一张嫦娥壁纸
→ 进入「神灵：嫦娥」
→ 查看「神域：月宫」
→ 阅读「神话：嫦娥奔月」
→ 回到相关视觉作品
→ AI 创作自己的嫦娥版本
```

这条链路同时满足：

- 视觉浏览；
- 世界观沉浸；
- 知识理解；
- SEO / GEO；
- AI 创作上下文复用。

## 6. 命名规范

用户界面统一使用：

```text
Character → 神灵
Realm / Scene → 神域
Story / Legend → 神话
Mythology → 文明 / 神话体系（作为分类时）
Artwork → 作品
Create → AI 创作
```

避免以下混用：

- 不再把 Character 一级入口叫「角色」；
- 不再把 Realm 一级入口叫「世界」；
- 不再把 Mythology 列表直接叫「文明图鉴」；
- 不使用「神话」同时指代文明分类和具体故事而不加上下文。

技术文档中：

- `Mythology` 始终表示文明 / 神话体系；
- 具体故事使用 `Story` / `MythStory`；
- 用户 UI 可以显示「神话」。

## 7. 视觉与内容占比

### 神灵

建议：视觉 75% / 文字 25%。

文字只承担身份说明、神职、符号、关系和简要背景。

### 神域

建议：视觉 75% / 文字 25%。

文字用于世界概览、地标说明、空间关系和背景。

### 神话

建议：文字 65% / 视觉 35%。

视觉用于：

- 故事首图；
- 章节插图；
- 人物 / 神域关系提示；
- 氛围分隔；
- 相关视觉作品承接。

禁止将神话页面重新做成大图卡片墙。

---

## 8. 产品设计验收问题

后续任何页面设计都应先回答：

1. 这是让用户「看」还是让用户「读」？
2. 主要对象是神灵、神域、神话故事还是作品？
3. 文明是内容主体还是筛选 / 上下文？
4. 页面是否与另外两个一级内容 Tab 明确区分？
5. 是否能自然跳转到相关神灵、神域、神话和作品？
6. 是否继续保持 MythCanvas 的 Image-first 原则，同时允许神话页成为明确的 Text-first 例外？

若一个页面同时平均承担所有职责，默认视为信息架构失焦。
