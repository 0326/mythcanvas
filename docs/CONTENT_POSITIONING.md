# MythCanvas 内容定位与一级导航规范

> 状态：Product Canonical Addendum  
> 版本：V1.1  
> 日期：2026-08  
> 适用范围：后续产品设计、页面命名、信息架构、内容建模与 AI Coding。

## 1. 结论

MythCanvas 的一级内容导航统一收敛为：

```text
首页｜探索｜神灵｜神域｜神话｜AI 创作
```

其中三类核心内容页面形成明确分工：

| 用户名称 | 核心问题 | 内容形态 | 主要对象 |
|---|---|---|---|
| 神灵 | 谁存在于神话中？ | 强视觉 | Character |
| 神域 | 神话发生在哪里？ | 强视觉 | World + Scene |
| 神话 | 我想了解哪一个神话体系？ | 视觉体系与实体聚合 | Mythology |

产品体验原则可概括为：

> **探索负责“发现作品”；神灵、神域负责“进入视觉实体”；神话负责“认识神话体系”；AI 创作负责“创造”。**

这套职责边界作为后续页面设计的默认前提。

---

## 2. 为什么不再使用「角色 / 世界 / 文明图鉴」

### 2.1 「角色」改为「神灵」

「角色」是产品与游戏术语，缺少 MythCanvas 自身的神话语义。

「神祇」虽然更古典，但认知门槛高、语义偏窄，无法自然覆盖英雄、妖灵、精怪、半神和其他具名神话存在。

因此用户侧统一使用 **神灵**，其产品解释为：

> 探索诸神、英雄与传说中的存在。

技术对象仍沿用 `Character`，不因用户名称改变数据模型命名。

### 2.2 「世界」改为「神域」

「世界」过于泛化，无法体现产品内容特征。

「神域」用于承载神话空间与视觉场景，包括：

- 神界 / 冥界 / 天界等大世界
- 奥林匹斯、阿斯加德、天宫、高天原等 Realm
- 月宫、昆仑、世界树之根、冥界之门等地点与 Scene
- 神殿、遗迹、战场、异象等可持续扩展的视觉空间

技术上保持 `Realm` 与 `Scene` 两层对象，用户侧统一由「神域」作为入口组织。

### 2.3 「文明图鉴」改为「神话」

「文明图鉴」的问题是：

- 容易被理解为百科目录；
- 与视觉产品的核心体验割裂；
- 把「华夏 / 希腊 / 北欧」这种分类维度误当成一级内容对象；
- “文明”容易让用户误以为这里是历史百科，而不是神话世界入口。

新的「神话」定位是 **Mythology 神话体系入口**：

> 进入一个完整的神话体系，认识它的神灵、神域、视觉 DNA、作品与相关传说。

具体故事、传说和事件属于独立的 `MythStory` 内容实体，后续可以作为神话体系下的故事模块或独立“故事 / 传说”入口，但不替代 `Mythology`。

## 3. 文明的正确定位：全站分类轴，而不是一级 Tab

华夏、希腊、北欧、日本、埃及等 `Mythology` 是一级内容实体，同时也是横向组织全站内容的 **神话体系上下文与分类轴**。

```text
                华夏神话
                    │
希腊神话 ───── Mythology ───── 北欧神话
                    │
                 日本神话
                    │
                 埃及神话

                    ↓
       ┌────────────┼──────────────┐
       ↓            ↓              ↓
      神灵          神域          神话故事
   Character      World / Scene   MythStory
       ↓            ↓              ↓
       └──────── Artwork / Related Content ────────┘
```

因此：

- `Mythology` = 神话体系实体 / 内容上下文 / Visual DNA 所有者；
- `Character` = 神灵；
- `World + Scene` = 神域；
- `MythStory` = 神话体系下的具体故事 / 传说；
- `Artwork` = 可以关联任意上述对象的视觉作品。

### 神话体系入口

神话体系通过 `/mythology/` 进入，并通过以下方式连接全站：

- `/mythology/` 神话体系列表；
- `/mythology/{slug}/` 神话体系聚合页；
- 神灵页和神域页筛选条件；
- 探索页 Artwork 筛选条件；
- 神话体系下的 MythStory / 传说模块；
- 搜索分组；
- 首页专题入口；
- Civilization Visual DNA 的技术归属对象。

## 4. 一级导航职责

### 首页

负责品牌感知和少量精选入口，不承担完整内容浏览。

### 探索

定位：**视觉内容发现 Feed**。

回答：

> 现在有什么值得看的神话视觉？

主要内容：Artwork；支持文明、类型、画风、设备、排序等筛选。

### 神灵

定位：**神话人物视觉资产库**。

回答：

> 我想认识和继续探索某个神话人物。

主要内容：Character Canonical Design、变体、相关神域、相关神话、Artwork。

页面应保持强视觉，以肖像 / 全身视觉作为主体。

### 神域

定位：**神话世界、地点和场景的视觉探索入口**。

回答：

> 这些传说发生在哪里？这个世界是什么样子？

主要内容：Realm、Scene、地标、空间结构、相关神灵、相关神话、Artwork。

页面应保持强视觉，以环境概念图和空间关系作为主体。

### 神话

定位：**神话体系与世界观入口**。

回答：

> 这是哪个神话体系？它包含哪些神灵、神域与视觉规则？

主要内容：Mythology、Civilization Visual DNA、相关神灵、神域、Artwork，以及后续接入的 MythStory。

页面以视觉体系和实体关系为主，不把具体故事正文冒充成 Mythology 本身。

### AI 创作

定位：把神灵、神域、画风和输出规格组合为新的视觉作品。

## 5. 核心产品关系

未来推荐链路围绕神话体系、视觉实体和作品互相跳转：

```text
Artwork
  ↔ 神灵 Character
  ↔ 神域 World / Scene
  ↔ 神话体系 Mythology
  ↔ 神话故事 MythStory
```

典型用户路径：

```text
看到一张嫦娥壁纸
→ 进入「神灵：嫦娥」
→ 查看「神域：月宫」
→ 进入「神话：中国神话」
→ 阅读相关「传说：嫦娥奔月」
→ 回到相关视觉作品
→ AI 创作自己的嫦娥版本
```

这条链路同时满足：

- 视觉浏览；
- 世界观沉浸；
- 知识理解；
- SEO / GEO；
- AI 创作上下文复用。

## 6. 命名规范

用户界面统一使用：

```text
Character → 神灵
World / Scene → 神域
Mythology → 神话 / 神话体系
MythStory → 故事 / 传说
Artwork → 作品
Create → AI 创作
```

避免以下混用：

- 不再把 Character 一级入口叫「角色」；
- 不再把 Realm 一级入口叫「世界」；
- Mythology 列表统一叫「神话」或「神话体系」；
- MythStory 在用户界面叫「故事」或「传说」，不与 Mythology 共用“神话”一级名称。

技术文档中：

- `Mythology` 始终表示神话体系；
- 具体故事使用 `MythStory`；
- 用户 UI 的「神话」指向 Mythology，故事使用「故事 / 传说」。

## 7. 视觉与内容占比

### 神灵

建议：视觉 75% / 文字 25%。

文字只承担身份说明、神职、符号、关系和简要背景。

### 神域

建议：视觉 75% / 文字 25%。

文字用于世界概览、地标说明、空间关系和背景。

### 神话

建议：视觉 65% / 文字 35%。

视觉用于：

- 建立神话体系氛围；
- 展示文明 Visual DNA；
- 呈现神灵、神域与 Artwork 关系；
- 承接后续故事 / 传说内容。

具体 MythStory 详情页才是文字优先的阅读页面。

---

## 8. 产品设计验收问题

后续任何页面设计都应先回答：

1. 这是让用户「发现作品」、进入实体，还是阅读故事？
2. 主要对象是 Mythology、神灵、神域、MythStory 还是 Artwork？
3. Mythology 是否承担了神话体系上下文，而不是被误当成单个故事？
4. 页面是否与另外两个一级内容 Tab 明确区分？
5. 是否能自然跳转到相关神灵、神域、神话和作品？
6. 是否继续保持 MythCanvas 的 Image-first 原则，并将 Text-first 留给未来的 MythStory 页面？

若一个页面同时平均承担所有职责，默认视为信息架构失焦。
